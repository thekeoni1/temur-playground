# Sandbox v1, P1: the shipped temur binary boots and runs under v86

2026-09-05. Local only. Nothing here is pushed or published.

## Result

The PUBLIC v0.33.0 i686 release binary, unmodified, boots inside v86 under
node and runs. Three of the four boot proofs pass outright. The fourth (the
TUI) draws correctly and then exits after one frame; the cause is known,
measured, and is a property of the guest KERNEL CONFIG, not of temur or of
v86. See "What fought back".

## Image recipe

This box has no `cpio` and no sudo to install one, and the guest needs the
binary owned by root:root. Rather than unpack and repack the laptop's
verified rootfs (which as a non-root user would rewrite every ownership in
it), the binary is APPENDED as a second initramfs segment:

  tools/mkcpio.py writes a newc archive holding usr/, usr/bin/ and
  usr/bin/temur with uid 0, gid 0, mode 0755
  gzip -9 that archive
  cat kit/rootfs.cpio.gz temur-overlay.cpio.gz > rootfs-temur.cpio.gz

The kernel concatenates initramfs segments and later entries win, so the
laptop's image is byte-for-byte untouched inside the result. Confirmed in
the guest: `-rwxr-xr-x 1 root root 6201908 /usr/bin/temur`.

## The four boot proofs

a. SHELL PROMPT: PASS. busybox root shell on ttyS0.
   "Starting network: FAIL" appears in every boot and is expected on this
   rung: the kernel has no networking at all.

b. `temur --version`: PASS.
     # temur --version
     temur 0.33.0

c. `temur doctor` offline: PASS. Runs, reports, does not crash.
   With no config it declines cleanly:
     FAIL: no config file at /root/.config/temur/config.json; run temur
     init to create a starter config
     doctor: 0 pass, 0 warn, 1 fail
   With a minimal openai-compat config written in the guest:
     PASS: config parsed / active selection / credentials keyless /
     key isolation / install (the temur on PATH is this running binary,
     temur 0.33.0) / sessions dir / prompt floor (estimate)
     FAIL: unreachable: http://127.0.0.1:8080/v1: TCP connect failed:
     Function not implemented (os error 38)
     doctor: 7 pass, 0 warn, 1 fail
   The one failure is the absent server, which is the designed state of
   this rung. `temur init` was NOT used: it is an interactive wizard and
   blocks on stdin, so the config was written directly.

d. PLAIN `temur` TUI: PARTIAL, and this is the honest result.
   It draws. One full frame reaches the serial console: the "# new
   session" title, "local . temur 0.33.0" in the top right, the yellow
   prompt-profile warning, the "> ask anything... (exit to quit)" input
   line, the "enter send / history / pgup-pgdn scroll / ctrl+c quit" help
   line, and the "/root ... local . thinking off . session" status line.
   Then it leaves the alternate screen and returns to the shell after that
   single frame. Empty stderr, no panic, no crash, but exit status 1.
   It does not stay up to be quit deliberately, so "quit cleanly" is
   recorded as NOT SHOWN rather than claimed.

## The five measurements

1. Boot to shell prompt, 128 MB: 3,826 to 4,294 ms over 8 boots,
   median about 4.0 s.
2. `temur --version` inside the guest: 0.01 s by busybox `time`
   (0.00 s user, 0.00 s sys). Host-side round trip including serial echo:
   22 to 38 ms.
3. Guest RAM: 128 MB works, as does 96, 80 and 72 MB. 64 MB does NOT boot,
   and fails on the EMULATOR side before the guest starts:
   `RangeError: offset is out of bounds` thrown inside v86's own init.
   So the floor sits between 64 and 72 MB, and 128 MB has ample headroom
   (`free -m` in the guest at 128 MB: 104 total, 8 used, 89 free).
4. Image file size: rootfs-temur.cpio.gz 3,892,250 B, up from the stock
   984,705 B. bzImage is unchanged at 3,015,168 B. Total to ship a
   bootable temur guest: 6,907,418 B.
5. State snapshot: saved at the shell prompt, 31,567,692 B
   (sha256 b25b313e4042bc05e11f4cb4ab393d36719b6d0e9883a991ec4ec82bbde20601).
   A FRESH node-v86 instance restores it in 102 ms and temur still runs
   there: `temur --version` answers "temur 0.33.0" 1,024 ms after process
   start, against about 4.2 s for a cold boot. Restore is roughly 4x
   faster to a working temur than booting.

## What fought back

THE TUI EXIT, root-caused. The guest kernel is built with
`# CONFIG_NET is not set`. That removes `socket()` entirely, which is why
doctor's TCP probe reports "Function not implemented (os error 38)". It
also removes AF_UNIX, because CONFIG_UNIX lives under CONFIG_NET. Crossterm's
event reader needs a unix socketpair for its signal plumbing, so the first
poll of the event source errors, temur's render loop takes its
`source_failed` path, sends None to the agent thread and shuts down. That
path is a deliberate clean shutdown for an unusable terminal, which is
exactly why there is no panic and no message. Enabling CONFIG_NET in the
Buildroot kernel config, with no network devices, should be enough to make
the TUI stay up; that is a P2 input, not a P1 fix.

NO CPIO, NO SUDO. Resolved by writing the newc archive directly
(tools/mkcpio.py) and appending it rather than repacking.

`temur init` IS INTERACTIVE. It blocked on stdin and timed out the harness
once. The config is written directly instead.

HARNESS BUGS, both mine, both fixed and worth recording because they
produced plausible-looking wrong output before they were caught:
  - the step sentinel was matched per received byte, so one step reported
    five times and the script never advanced;
  - a command whose output had no trailing newline put the sentinel
    mid-line, where the anchored regex could never match, and the run hung
    to the timeout. The harness now prints a bare newline before every
    sentinel.

SERIAL TTY SIZE. `stty size` fails on ttyS0 and TERM arrives as vt100. Until
`stty rows 24 cols 80` is set, temur exits immediately with no frame at all.
The frame in proof (d) only exists because the size is set first.
