# The file panel takes 16 MiB per file and 64 MiB in total

Built on the laptop from /home/dev/playground-filecap-kickoff.md, verified
by sha256 (e2fba907...) before any work started.

Keyless throughout. No session saw, typed, stored or read a key. Nothing
is pushed: the commit is local and held for the operator's word.

## Verdict

The caps are raised and the gate that allowed it passed on both tiers.

    FILE_MAX_BYTES    8388608  ->  16777216   (8 MiB  -> 16 MiB)
    SHARE_MAX_BYTES  33554432  ->  67108864   (32 MiB -> 64 MiB)

This is page-only. MEM_MB stays 128, the snapshots are the same p7 pair
the v0.34.0 refresh shipped, and relay/ is untouched.

## The gate, and why it was the right question

The files live in the visitor's tab and never reach a server, so raising
the caps costs that visitor's memory and nothing else. The one place it
could actually break is inside the guest: temur's office reader pulls one
document into a machine with 128 MB of RAM and extracts it there.

Reading temur's own limits first settled what the measurement had to be.
`src/tools/office.rs` accepts anything up to 32 MiB (`MAX_INPUT_BYTES`),
so a 16 MiB file is NOT refused early, and extraction really runs. The
read tool's output is capped at 28 KB (`read.rs MAX_BYTES`), so the text
coming back is small either way. The expensive path is the spreadsheet
one: it goes through `calamine::open_workbook_auto` rather than the
`zip_entry_to_string` helper, so the 64 MiB `MAX_UNZIPPED_BYTES` ceiling
does not apply to it, and `spreadsheet()` builds the text of every row of
every sheet with no early stop. A PDF, by contrast, stops once the
caller's window is full. So the spreadsheet was always going to be the
one that decided this.

## The documents

Generated by tools/mkbig-sample.py, which is new and works the way
tools/mkdocs-sample.py does: hand-built, deterministic, and padded to
size. Random bytes would have been useless, because temur refuses a
malformed PDF before it parses anything.

    big.pdf    16,264,413 B   15.51 MiB   1,098 pages
    big.xlsx   16,317,903 B   15.56 MiB   148,801 rows

The spreadsheet's compressibility is controlled on purpose. Padding it
with one repeated word would deflate 50x, and the measurement would then
be of a decompression bomb rather than of a large workbook. Its cells
carry pseudo-random tokens from a seeded PRNG, which puts the ratio at
4.45x: 72,638,765 bytes of sheet XML behind a 15.56 MiB file. That is the
range a real sheet full of unique IDs gives.

Each carries a distinctive first line, `BIG-PDF-PAGE-ONE-MARKER` and
`BIG-XLSX-ROW-ONE-MARKER`, so a clean read is an exact match rather than
a resemblance.

## A host pre-check first, to avoid spending emulator time on a guess

The shipped i686 musl binary runs natively on this machine, so both reads
were driven there first with `--mock`, which is the same pointer width and
the same allocator the guest uses.

    big.pdf     read OK   peak RSS 40,704 kB   0.17 s
    big.xlsx    read OK   peak RSS 79,104 kB   1.75 s

79 MB of peak against a 128 MB guest is tight enough to be worth
measuring properly and not tight enough to abandon the raise.

## The measurement

tools/proof-bigfile-read.mjs, new, and the mechanism is
tools/proof-office-read.mjs unchanged in substance: files arrive through
`emulator.create_file`, which is the page's own drop path, and a scripted
model (tools/guest-stub-model.sh, reused exactly as committed) stands on
guest loopback because no temur surface ever prints tool output. The
request bodies temur sends are written into the share and read back over
9p, so what is checked is the guest's own bytes.

Two turns per tier, not one, because the memory had to be read between
the two reads.

### Both tiers passed

    OFFLINE (NO PROVIDER)         big.pdf              big.xlsx
      outcome                     clean read           clean read
      marker returned             yes                  yes
      read time                   5.8 s                29.0 s
      guest alive afterwards      yes                  yes
      OOM / panic signs           none                 none

    NETWORKED                     big.pdf              big.xlsx
      outcome                     clean read           clean read
      marker returned             yes                  yes
      read time                   5.5 s                29.5 s
      guest alive afterwards      yes                  yes
      OOM / panic signs           none                 none

Both reads on both tiers returned extracted text with the marker intact.
Neither tier needed temur's size refusal, because 15.5 MiB is inside
temur's own 32 MiB limit.

### Guest memory, the three points

                                    MemFree      MemAvailable
    OFFLINE
      1  before the drop            81.7 MB      79.6 MB
         after the drop             81.7 MB      79.6 MB
      2  after reading big.pdf      77.3 MB      75.2 MB
      3  after reading big.xlsx     75.5 MB      73.4 MB

    NETWORKED
      1  before the drop            81.6 MB      79.6 MB
         after the drop             81.6 MB      79.6 MB
      2  after reading big.pdf      77.3 MB      75.3 MB
      3  after reading big.xlsx     75.3 MB      73.3 MB

THESE THREE POINTS DO NOT ANSWER THE OOM QUESTION, and reporting them
alone would have overstated the headroom. They are taken after each read,
by which time the allocator has given the pages back: both tiers moved
MemFree by about 6 MB across both documents while the same binary peaked
at 79 MB of RSS on the host. So a sampler was added that reads
/proc/meminfo once a second in the guest for the length of the turn, and
the minimum it sees is the real figure:

                          lowest MemFree    lowest MemAvailable   samples
    OFFLINE
      big.pdf             51.1 MB           49.0 MB               7
      big.xlsx            24.8 MB           22.8 MB               30
    NETWORKED
      big.pdf             51.0 MB           49.0 MB               7
      big.xlsx            26.6 MB           24.6 MB               30

22.8 MB spare is the smallest margin either tier showed. The two tiers
agree to within 2 MB, which is the main reason to believe the number. A
sampler reading once a second can miss a shorter spike, so the true
minimum may be somewhat lower, and 16 MiB should be treated as near what
this guest will take rather than comfortably inside it.

The drop itself cost the guest nothing measurable: 31.07 MiB of documents
written through `create_file` in 45 ms moved MemFree by 0 MB on both
tiers. That is the 9p filesystem living in the tab rather than in the
guest's RAM, and it is why the 64 MiB share total is the cheaper of the
two caps.

Records: build/proof-bigfile-read-offline.json and
build/proof-bigfile-read-networked.json.

## The rationale comment

page/app.js carried the old reasoning in full ("8 MiB per file is where a
file stops being something the guest can pick up briskly ... 32 MiB in
total keeps the whole share well inside a guest that has 128 MB of RAM").
Raising the caps and leaving that would have made the comment false, so
it is rewritten around the measurement above, and it now says which of
the two caps is the dangerous one and why.

## Page checks, both tiers

Headless Edge, real time, local relay supplied by PAGE_DEV_RELAY at serve
time. The shipped page/_headers CSP is unedited and 0-diff. Each report
is deleted before its run by tools/page-run.sh, so no stale verdict could
read as a result.

The tier follows relay reachability, there is no override, so each tier is
a separate pass with the relay up or down. The relay-down pass ran FIRST
so that the committed reports keep describing the same tier they described
at v0.34.0.

    NO PROVIDER tier (relay down)
      filecheck      ok: true    caps 16777216 / 67108864, both refusals fired
      textcheck      ok: true    17 terms, 0 in markup, 0 in rendered text
      landingcheck   n/a         gated on the networked tier by design
      selftest       ok: true    wire 16,046,502, state 38,851,288,
                                 readyMs 3321, offline greeting intact,
                                 echo 1 ms

    Networked tier (relay up)
      filecheck      ok: true    caps 16777216 / 67108864, both refusals fired
      textcheck      ok: true    17 terms, 0 and 0
      landingcheck   cleanLanding true, wizardAtFirstQuestion true,
                     readyMs 2010, stamp reads build 5a315cd
      netcheck       wire 16,946,323, state 39,805,664, readyMs 1992,
                     "PASS: reachable: https://api.anthropic.com
                      (TCP connect + TLS handshake)"

filecheck is the one that proves the change, and it proves it twice: the
caps it read back are 16777216 and 67108864, an over-cap file was refused,
and a file that would cross the total was refused after the share held
50,462,720 bytes. textcheck's report came back byte-identical to the
committed one, so the comment rewrite introduced no diagnostic term and no
markup change.

netcheck and selftest report the exact wire and state sizes of the p7
pair, which is the check that the page is still serving those snapshots.

landingcheck does not run on the offline tier: page/app.js gates it on
`networked` and the function hardcodes `tier: "networked"`, because the
wizard it looks for is the networked tier's landing. Its absence there is
the design, not a regression, and its networked report matches the
committed one except for readyMs.

## Flagged

1. fmtBytes LABELS MiB VALUES AS "MB". page/app.js:850 divides by
   1024*1024 and prints "MB", so the refusal now reads "larger than the
   16.0 MB limit" for a 16 MiB cap. The mislabel predates this change and
   the kickoff puts it out of scope, so it stands.

2. #fileshint IS UNCHANGED, and needs no edit. page/index.html:251-253
   carries no size at all. The only size-facing text is the two refusal
   messages, and both build their number through fmtBytes, so they
   self-updated to 16 and 64. If the hint should advertise the new size,
   that wording has to arrive before the ship.

3. build/bigfiles/ WAS NOT IGNORED, AND NOW IS. tools/mkbig-sample.py
   writes 31 MiB of generated documents there and nothing kept them out
   of a public repository, so a `git add -A` would have swept them in.
   The v0.34.0 refresh had added `build/office/` for exactly this class of
   sample, but .gitignore was on this kickoff's 0-diff list, so it was
   raised rather than edited without a word. It was then approved and
   closed in a fourth commit, beside build/office/:

       # The near-cap documents the file-cap gate generates.
       build/bigfiles/

   Proved rather than assumed: `git check-ignore -v` matches both
   documents at .gitignore:33, and with all 31 MiB of them present
   `git status` reports only tracked changes.
