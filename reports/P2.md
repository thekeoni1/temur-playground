## Step 0: the CONFIG_NET rebuild

### Root cause, confirmed rather than assumed

P1 diagnosed this correctly. Confirmed independently here, in the kernel
source rather than by inference: in net/Kconfig, `menuconfig NET` is a bare
`bool "Networking support"` with NO `default y`, and in net/unix/Kconfig,
`config UNIX` is likewise a bare bool. The laptop's kernel config is a
sparse 47-line fragment that Buildroot runs olddefconfig over. Because
neither symbol carries a default, never mentioning NET did not leave it at
some benign default: it took `n`. That removed socket() outright, which is
where doctor's "Function not implemented" came from, and it removed AF_UNIX
with it, because CONFIG_UNIX sits inside `if NET`. crossterm's event reader
needs a unix socketpair, so its first poll failed and temur took its
`source_failed` clean-shutdown path after one frame.

### The change

Appended to /home/dev/v86-guest-2026-09-04/linux-i686-v86.config
(input config sha256 c136961b... -> dfc245510ddc13d704e399c4affec2e38d2e12
c2bab926948c08f502457eeeea):

  CONFIG_NET=y
  CONFIG_UNIX=y
  CONFIG_INET=y
  # CONFIG_NETDEVICES is not set
  # CONFIG_IPV6 is not set
  # CONFIG_NETFILTER is not set
  # CONFIG_BRIDGE is not set
  # CONFIG_VLAN_8021Q is not set
  # CONFIG_INET_DIAG is not set
  # CONFIG_IP_MULTICAST is not set
  # CONFIG_IP_ADVANCED_ROUTER is not set
  # CONFIG_INET_TUNNEL is not set

CONFIG_INET IS A DELIBERATE ADDITION BEYOND THE SPEC'S LITERAL WORDS, and
planning should confirm it. The spec asked for NET and UNIX, and separately
predicted that doctor's TCP probe would come back as connection-refused.
Those two do not meet: without CONFIG_INET there is no AF_INET, so a TCP
connect to 127.0.0.1 fails with EAFNOSUPPORT, not ECONNREFUSED. INET is what
makes the spec's own stated proof reachable. It adds no device driver and no
route off the machine; the guest still cannot reach anything but itself.

Verified in the built .config:

  CONFIG_NET=y
  CONFIG_UNIX=y
  CONFIG_INET=y
  # CONFIG_PACKET is not set
  # CONFIG_IPV6 is not set
  # CONFIG_NETFILTER is not set
  # CONFIG_NETDEVICES is not set

and verified in the running guest: /proc/net/protocols lists UNIX-STREAM,
UNIX and TCP; `ip link` shows exactly one interface, `lo`, UP at 127.0.0.1.
No NIC of any kind.

## Step 2: the page shell

page/index.html + page/app.js, served by tools/serve-page.mjs on
127.0.0.1:8088. Components, all pinned, all local:

  - v86 browser build: page/vendor/libv86.js + v86.wasm, copied from the
    SAME 0.5.458 npm package the node harness uses;
  - the laptop's seabios.bin / vgabios.bin blobs;
  - xterm.js 6.0.0, wired to the emulated serial port in both directions
    by hand: guest bytes are batched per animation frame and written to
    the terminal, terminal input is UTF-8 encoded and fed to
    serial0_send byte by byte;
  - fixed geometry 80x24, set by stty inside the snapshot BEFORE temur
    ever launches. Dynamic resize is deliberately NOT implemented; see
    "out of scope" below;
  - snapshot restore path: the page fetches the gzipped snapshot, counts
    the bytes as they arrive, gunzips it with the browser's own
    DecompressionStream, restores it into a fresh emulator, runs, and
    sends the temur launch line. The user lands at a live temur prompt
    with no keypress needed;
  - a minimal loading indicator: a byte counter with a progress bar, then
    "restoring", then a ready line carrying the timings. No design work.

### The page does not download the kernel or the initrd

restore_state carries full memory and device state, so bzImage and the
initrd are dead weight on the restore path. Proved before relying on it
(tools/restore-nokernel.mjs restores and runs temur with neither passed to
the constructor). That removes 7,685,658 B, about 29%, from what the page
would otherwise fetch.

### How the browser result was proved

This session has no GUI, so the page proves itself: opened with
?selftest=1 it drives its own keyboard and POSTs what it actually rendered
back to the local server, which writes build/page-selftest.json. The
evidence is the literal xterm buffer text at four points, not a screenshot
and not an assertion. In the last run:

  - after launch: the full temur frame, "# new session" titled, the
    prompt-profile warning, the input line, the help line and the status
    line, all laid out inside 80x24;
  - after typing: the input line reads "> hello from p2";
  - after 13 DEL bytes: the input line is back to its placeholder;
  - after typing exit and pressing Enter: the buffer is just the shell,
    "TERM=xterm temur" and a "# " prompt. temur left cleanly.

So the browser reproduces proof (d) end to end, not merely "the page
renders something".

An operator with a screen can see the same page headed with:

  node tools/serve-page.mjs 8088
  then open http://localhost:8088/ in any browser on the machine

## What fought back

CONFIG_INET, THE GAP IN THE BRIEF. Covered above. NET+UNIX alone would have
fixed the TUI but left doctor reporting EAFNOSUPPORT, and the spec asked for
connection-refused. Flagged rather than quietly decided.

HOST-FLEX BLOCKED THE FIRST REBUILD. `make linux-reconfigure` died in 15
seconds in a package nobody touched: host-flex re-extracted its source, which
made its .stamp_patched stale, but the .applied_patches_list left in the
build directory by the P1 run survived the re-extraction. apply-patches.sh
read that list, saw its own patch already named in it, and refused with
"duplicate filename", pointing at the same path twice. The freshly extracted
tree had no patches applied at all, so the list was simply stale; removing
that one file let the build run. The kernel itself then took 1m40s.

NODE WAS INVISIBLE, NOT ABSENT. P1's node v24.20.0 is still installed under
~/.nvm, but nvm only loads from ~/.bashrc in interactive shells, so it is
not on the PATH of a non-interactive tool-call shell, and it is certainly
not on the sanitized clean-POSIX PATH that Buildroot requires. Rather than
depend on shell startup files, a second copy of the SAME version was
installed PATH-independently under ~/.local/opt, sha-verified against
nodejs.org. Both now exist; the ~/.local/opt one is what every command here
used. (Caught by planning, who knew where P1 had put it.)

PYTHON'S http.server WOULD HAVE CORRUPTED THE MEASUREMENT. Its mimetypes
table maps .gz to Content-Encoding: gzip, so the browser would have
transparently gunzipped the snapshot and then the page's own
DecompressionStream would have been handed already-decompressed bytes. The
page would have broken, or worse, worked while reporting the wrong transfer
size. tools/serve-page.mjs sends every file verbatim as
application/octet-stream with no Content-Encoding, and logs each asset's
byte count so the page's own total can be checked from the server side.

CONTROL BYTES AND QUOTING. The step scripts embed a JSON config inside a
shell single-quoted string inside a JSON string, and the erase steps need
literal DEL bytes. Building those through bash -c lost every round; they
are generated by small committed scripts instead. In the page source the
DEL run is written String.fromCharCode(127).repeat(13) rather than as a raw
byte, so nothing invisible ends up committed.

A pkill -f "serve-page.mjs" MATCHED ITS OWN SHELL and killed the command
that ran it. Harmless, and only worth recording because the exit code (144)
looks alarming and means nothing.

## An observation for planning, not a defect

temur 0.33.0 DOES enable bracketed paste: the serial capture shows
ESC [ ? 2004 h immediately after it enters the alternate screen, and
ESC [ ? 2004 l on the way out. Dogfood finding item 11 was recorded against
a much older build and says there is no bracketed paste. Nothing here
exercised pasting, so this is only a note that the old finding's premise
looks stale and may be worth re-checking against a current build. No temur
behaviour was investigated or changed in this phase.

Nothing else looked like a temur defect. Every problem in this phase was an
environment problem.

## Out of scope, confirmed untouched

No guest networking beyond loopback (P3 owns the relay; there is still no
NIC in the kernel). Nothing hosted or published; the server binds 127.0.0.1
only. No WebLLM. No page design or copy. NO DYNAMIC TERMINAL RESIZE: the
snapshot's stty is baked at 80x24 and temur reads its size once at startup,
so a browser-side resize would silently desync the guest from the terminal.
That is the reason it is skipped, not merely that it was not asked for. No
temur code change of any kind, and the temur repo was never written to.
