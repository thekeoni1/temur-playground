# P6: file transfer over 9p

Built on the laptop from the desktop brief (sandbox-9p.md) and the
laptop kickoff derived from it. Both were verified by sha256 before any
work started, and they agree; where this report differs from either, it
is a disclosed deviation in the numbered list at the end.

Keyless throughout. No session saw, typed, stored or read a key. The
temur product tree was not touched. Nothing is pushed: every commit
below is local and held for the operator's word.

## Verdict

Scope items 1 to 5 are built and proven on both tiers. Item 6, the trust
sentence, is GATED and is NOT in any commit here; its wording is staged
verbatim for the two-half sign-off and this report does not put it on
the page.

The visitor can now drop a file onto the terminal, have temur work on it
in its own working directory, and take the result back out, on a machine
that still needs no server, no account and no install.

## What the spike promised and what held

The mount survives save_state and restore_state untouched, because v86
serialises the 9p filesystem INTO the state: it is data, not a live
socket like the NIC, so both halves come back together. That held on our
own snapshots, on both tiers, and no remount was added anywhere. The
proof set proves survival rather than papering over its loss, which is
the console.sh lesson applied forward.

## THE FINDING THIS MILESTONE TURNED UP

"THE SHARE IS EMPTY AT THE SNAPSHOT POINT" IS NOT A SUFFICIENT RULE.

A file written into the share and then deleted leaves the directory
listing empty and ITS BYTES STILL IN THE SAVED STATE. Measured, not
feared: a marker string was written from the guest, removed with rm,
synced, the state saved, and the marker was still recoverable from the
state blob afterwards. v86 keeps the inode slot and save_state
serialises what it keeps.

That matters because the state is downloaded by every visitor. A
snapshot built after any file had been written and tidied away would
publish those bytes past an assert that only checked the listing.

So the rule implemented here is PRISTINE, not tidy. The detector is the
inode count, which is exactly 1 for an untouched filesystem, and a
listing that is empty over a higher count is refused with its own
message saying why. The practical constraint that follows is real: A
SNAPSHOT BUILD MAY NEVER WRITE INTO THE SHARE AT ALL, not even to test
it and clean up. Share read and write is exercised on the raw-boot run,
which saves no state.

This is stricter than the brief's item 4 and was relayed to planning as
a disclosed tightening rather than folded in quietly. It is deviation 1.

THE ASSERT'S OWN FIRST VERSION WAS WRONG, AND THE RED HALF IS WHAT
CAUGHT IT. GetRecursiveList takes an inode id and an output array, not a
path, so the first version threw on every filesystem and would have
refused the real build too. It refused the planted file for the wrong
reason, which read exactly like a pass. The rewrite cross-checks the
recursive walk against the top-level listing and refuses when they
disagree, because the silent form of that mistake is a false green, and
a false green here publishes files.

## Item 1: the kernel

Five symbols, added beside p4, never over it: CONFIG_9P_FS, CONFIG_NET_9P,
CONFIG_NET_9P_VIRTIO, CONFIG_VIRTIO, CONFIG_VIRTIO_PCI.

  kit/bzImage-p6              3,912,192 B   +90,112 B over p4
  kit/kernel-p6.config
  kit/linux-i686-v86-p6.config

VIRTIO returns after P3a deliberately left it off, which is not a
reversal of that decision. P3a chose ne2k for the NIC precisely so it
would not pay for VIRTIO_PCI while nothing needed it; 9p needs it
whatever the NIC is, so the cost is paid once and the NIC choice stands.
Reopening a settled network path is not what this milestone is for.

REPRODUCIBLE NOW, WHICH IT WAS NOT. The spike found that rebuilding
bzImage-p4 from a byte-identical .config gave the same size and a
different sha256: scripts/mkcompile_h stamps a build timestamp and an
incrementing counter into compile.h unless KBUILD_BUILD_* is pinned.

Buildroot pins them itself, but only under BR2_REPRODUCIBLE, which this
tree does not set and must not start setting, because that would change
the rootfs too and kit/rootfs.cpio.gz is an accepted artifact.
LINUX_MAKE_ENV overrides only PATH and GIT_DIR, so an exported
environment reaches the kernel's make untouched. tools/build-kernel.sh
sets exactly the values BR2_REPRODUCIBLE would have used, so a future
reproducible-mode build agrees with this one. It pins the PATH too,
which every kernel build in this programme has done by hand because the
inherited Windows entries kill Buildroot.

  build 2  680f7536ed2a14a45f4720cc4bd4583901d25182033c907ea8798dee01ea8868

## Items 2 and 3: the overlay, the share and the landing

The share is /files. One short path, printed by the MOTD and by the
page, and it is the login shell's working directory, so temur inherits
it and a dropped file is simply already in front of the agent.

  tools/guest/S30files    mounts at boot from /etc/init.d/rcS
                          host9p, trans=virtio,version=9p2000.L,msize=65536
  tools/guest/console.sh  gains a guarded cd into the share
  tools/guest/motd        gains one line naming it

ONE OVERLAY NOW SERVES BOTH TIERS, and that is the approved
offline-snapshot fix. console.sh had only ever reached the networked
image: the offline snapshot was built from the P2-era rootfs and never
received it or the MOTD, which is how an operator met Enter echoing as
^M on the live page. The page-side stty nudge stays as belt and braces
and is no longer load bearing.

No remount on restore, deliberately.

## Item 5: the page

A button plus drag and drop onto the terminal, and a list of the share's
files with a download beside each name. The panel appears only when the
machine is up. The emulator is constructed with filesystem:{}, because a
machine that restores a state carrying a mount still needs a device for
it to land in.

THE CAPS ARE MEASURED, NOT ASSUMED. create_file is nearly free, since it
writes into this tab: 3 ms at 1 MiB, 3 ms at 8 MiB, 15 ms at 16 MiB. The
cost that matters is the guest reading the file back, at roughly 200 ms
per MiB: 0.6 s at 1 MiB, 1.6 s at 8 MiB, 3.0 s at 16 MiB, with content
hashes matching at every size. So the brief's suggested 8 MiB per file
and 32 MiB in total survive their measurement as comfort limits rather
than correctness ones, and they are kept unchanged.

Over-cap is refused in one sentence, never truncated. The first refusal
sentence was itself a defect, caught by the browser check: naming both
rounded sizes made a file one byte over read as "is 8.0 MB and the limit
is 8.0 MB", which contradicts itself and makes the page look broken
rather than strict.

CSP: page/_headers is 0 diff. Nothing new is fetched. Downloads go
through a blob URL and a synthetic click, which the browser check
confirms does not throw under the shipped policy.

## Deviations, disclosed

1. THE EMPTY-AT-SNAPSHOT RULE IS STRICTER THAN ORDERED. The brief said
   the harness must assert the filesystem is empty. It asserts PRISTINE,
   because deleted bytes were measured surviving in the state and an
   emptiness check alone would have passed them. Relayed to planning
   before proceeding and accepted.

2. KBUILD_BUILD_USER AND KBUILD_BUILD_HOST ARE PINNED TOO. The brief
   named the timestamp and the version. Those two alone leave the build
   machine's user and hostname in the kernel banner, so the artifact
   would still not reproduce off this laptop. All four are pinned, to
   the values Buildroot's own reproducible mode uses.

3. THE MOUNT OPTIONS CARRY msize=65536. The brief gave
   trans=virtio,version=9p2000.L; the kickoff added the msize and the
   spike measured that value working. Recorded because the two source
   documents differ here and the kickoff is the narrower one.

4. THE SUPERSEDED SNAPSHOTS STAY COMMITTED. Add-beside is read
   literally: page/assets keeps the p5 and P2-era .gz files untouched
   beside the new pair, so the repository carries about 30 MiB it no
   longer serves. Dropping them is a separate decision and is left to
   planning.

5. TWO NEW PAGE CHECK MODES were added, filecheck and textcheck, which
   the brief did not ask for by name. The proof set it did ask for could
   not otherwise be run from a real browser on both tiers.
